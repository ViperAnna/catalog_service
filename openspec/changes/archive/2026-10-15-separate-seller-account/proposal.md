# Proposal

## Why

Сейчас продавец — это аккаунт покупателя с добавленной ролью SELLER: у него
USER и SELLER одновременно, функции покупателя и продавца смешаны. Решение
пользователя (2026-10-15, вариант 2): продавец работает в отдельном аккаунте
только с ролью SELLER (товары и продажи), а аккаунт покупателя остается
покупателем (вишлисты, корзина, заказы).

Решения пользователя:
- у одного покупателя не больше одного продавца;
- существующие продавцы (USER+SELLER на аккаунте покупателя) остаются как
  есть; функции покупателя им закрывает change `wishlist-access-and-limits`
  (правило «SELLER → 403»);
- при окончательном удалении продавца его аккаунт удаляется;
- отдельный change от `wishlist-access-and-limits`, frontend включен.

## What Changes

- Покупатель подает заявку REGISTRATION с контактным email E. E SHALL не
  принадлежать ни одному аккаунту Keycloak (в realm email уникален) —
  проверка при подаче и при одобрении (409).
- При одобрении user-service создает в Keycloak новый аккаунт: логин и email —
  E, только роль SELLER (без составной роли по умолчанию, где USER), письмо
  для установки пароля и подтверждения email. `Seller.keycloakUserId` — id
  нового аккаунта, `Seller.applicantKeycloakUserId` — id покупателя.
  **Изменение поведения одобрения.**
- Доступ seller-service: подача REGISTRATION — USER (покупатель); просмотр
  своих заявок — USER или SELLER; UPDATE, DELETION, UNBLOCK — SELLER.
- Окончательное удаление продавца удаляет его аккаунт Keycloak и заявки,
  включая регистрационную заявку покупателя. Для существующих продавцов
  (аккаунт покупателя) — как сейчас: снимается роль SELLER, аккаунт остается.
- Сбой после создания аккаунта откатывает одобрение и удаляет созданный
  аккаунт (компенсация); повтор одобрения переиспользует незавершенный
  аккаунт с тем же email.
- frontend: аккаунт без USER не видит профиль и вишлисты.
- Не входят: кабинет продавца во frontend (его нет и сейчас), перенос
  существующих продавцов, смена email входа через заявку UPDATE (Open
  Questions design.md).

## Capabilities

### New Capabilities
<!-- нет -->

### Modified Capabilities
- `seller-onboarding`: доступ к заявкам, ограничения регистрации (email),
  одобрение регистрации и удаления, gRPC-контракт, работа с Keycloak,
  откат и компенсация.
- `access-control`: модель ролей (аккаунт продавца только с SELLER), права
  клиента `user-service-admin`.
- `user-profile`: аккаунт продавца без USER не имеет профиля покупателя.

## Impact

- seller-service: модель Seller (`applicant_keycloak_user_id`), проверки и
  одобрение, удаление, `SpringSecurityConfig`/контроллер заявок, gRPC-клиент,
  `user.proto`.
- user-service: gRPC-сервер (создание, удаление, проверка email), Keycloak
  Admin API, `user.proto`.
- frontend: скрытие профиля и вишлистов для аккаунта без USER.
- Keycloak: конфигурация realm не меняется (SMTP уже настроен). В dev SMTP
  realm указывает на `smtp.mail.ru` — письма об установке пароля уйдут на
  реальные адреса (design.md R4).
- Конфликт архивации: `access-control` меняют также `add-order-service` и
  `user-service-jwt-issuer` (другие requirements); `seller-onboarding` — нет.
