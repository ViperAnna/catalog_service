# Proposal

## Why

Валидация API магазинов слабее ограничений таблицы `stores`, поэтому запрос
проходит валидацию и падает в БД с 500 (`seller-stores` OBS-03, OBS-04):
- `email` и `phoneNumber` в API необязательны, а в БД объявлены `NOT NULL`.
  Создание магазина без них дает 500;
- `description` в API допускает до 500 символов, а колонка `varchar(255)`.
  Описание длиной 256–500 символов дает 500.

Change S3 из разбора OBS `seller-stores`: API должно отклонять такие запросы
с 400 до обращения к БД.

## What Changes

- **Создание магазина (`POST /stores`):** `email` и `phoneNumber` становятся
  обязательными. Если их нет, ответ 400 вместо 500.
- **Формат телефона магазина** (и `POST`, и `PUT`): принимаются только
  `+7XXXXXXXXXX` и `8XXXXXXXXXX`. Форма `8XXXXXXXXXX` сохраняется как
  `+7XXXXXXXXXX`. Остальные формы, включая `7XXXXXXXXXX` без плюса, пробелы,
  скобки, дефисы и номера других стран, дают 400.
- **Лимит `description`** (и `POST`, и `PUT`): не длиннее 255 символов, как
  колонка `varchar(255)`. Более длинное описание дает 400 вместо 500.
- **Изменение магазина (`PUT /stores/{id}`):** `email` и `phoneNumber`
  остаются необязательными, частичное обновление (null не меняет поле)
  сохраняется. Если они переданы, к ним применяются те же правила формата.
  Для этого у `PUT` появляется собственный DTO запроса с теми же полями.
- Сообщения валидации на английском, как остальные сообщения seller-service.
- **BREAKING (API):** телефоны, которые раньше принимались по шаблону
  `\+?[0-9]{7,15}`, кроме `+7XXXXXXXXXX` и `8XXXXXXXXXX`, теперь отклоняются
  с 400. Описание длиной 256–500 символов теперь дает 400 вместо 500.
  Создание без email или телефона дает 400 вместо 500.

### Out of scope

- Формат тела ошибки 400. В seller-service нет `@ControllerAdvice`, поэтому
  тело остается стандартным телом Spring (S4, OBS-11).
- Уникальность имени магазина и проверка имени при `PUT` (S2, OBS-05,
  OBS-10). Обязательность `storeName` при `PUT` не меняется.
- Семантика `PUT` (D1, OBS-06), статус продавца (A2), жизненный цикл
  магазина (A1).
- Изменение схемы БД: колонки не расширяются, миграций нет.
- Нормализация уже сохраненных телефонов. В текущей БД один магазин, его
  телефон `+79990000002` уже в каноническом формате.
- Общий модуль нормализации телефона с user-service.

## Capabilities

### New Capabilities

_Нет._

### Modified Capabilities

- `seller-stores`: изменяются требования `Store creation`,
  `Store field validation` и `Store update`, добавляется требование
  `Store phone normalization`.

## Impact

- **seller-service:** `StoreRequest` (обязательность и форматы для `POST`),
  новый `StoreUpdateRequest` для `PUT`, `StoreController`, `StoreMapper`,
  `StoreServiceImpl` (нормализация телефона), небольшая утилита нормализации.
- **БД:** без изменений схемы.
- **catalog-service, frontend, Kafka, Keycloak:** без изменений. frontend
  `/stores` не вызывает.
- **Тесты:** в seller-service тестовая инфраструктура работает, тесты входят
  в change.
