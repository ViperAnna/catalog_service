# Proposal

## Why

Уникальность имени магазина в seller-service работает неправильно
(`seller-stores` OBS-05, OBS-10, ASM-01):
- при `PUT` проверка не исключает сам изменяемый магазин, поэтому `PUT` с
  текущим именем (в любом регистре) дает 409, и изменить описание, email или
  телефон без переименования нельзя;
- уникальность обеспечивается только проверкой в приложении, ограничения в БД
  нет, поэтому два параллельных запроса могут создать магазины с одинаковым
  именем;
- пробелы по краям имени не учитываются: `Shop` и `  Shop  ` считаются разными
  именами.

Архитектурное решение: имя магазина уникально в пределах одного продавца, без
учета регистра и пробелов по краям, и уникальность гарантирует БД. Это change
S2 из разбора OBS `seller-stores`.

## What Changes

- **Нормализация имени:** при создании и изменении storeName сохраняется без
  пробелов по краям (`trim`), регистр сохраняется для отображения.
- **Правило уникальности:** у одного продавца не может быть двух магазинов, у
  которых совпадает `lower(trim(storeName))`. `Shop`, `shop` и `  SHOP  ` для
  одного продавца — одно имя. Разным продавцам одинаковое имя разрешено.
- **Исправление `PUT`:** проверка исключает сам изменяемый магазин, поэтому
  `PUT` с текущим именем (в любом регистре и с пробелами) больше не дает 409.
- **Гарантия в БД:** уникальный функциональный индекс
  `uq_stores_seller_store_name ON stores (seller_id, lower(btrim(store_name)))`.
  Его создает `schema.sql` через встроенную в Spring Boot SQL-инициализацию
  (`spring.sql.init.mode=always`,
  `spring.jpa.defer-datasource-initialization=true`) командой
  `CREATE UNIQUE INDEX IF NOT EXISTS`. Скрипт выполняется после
  `ddl-auto: update`, а повторный старт не падает.
- **Гонка:** нарушение индекса (`SQLState 23505`, индекс
  `uq_stores_seller_store_name`) переводится в 409 `STORE_ALREADY_EXISTS`, как
  и проверка в сервисе.
- Не BREAKING. Единственное видимое изменение — исчезновение ложного 409 при
  `PUT` и 409 вместо возможного дубля при гонке.

### Out of scope

- Модерация изменений имени, телефона и email магазина и неизменяемость ИНН
  продавца. Это отдельные будущие change.
- Тело ответа 409. Остается стандартное тело Spring, потому что в
  seller-service нет `@ControllerAdvice` (S4, OBS-11).
- Flyway или другие инструменты миграций. `schema.sql` содержит только
  идемпотентную команду создания индекса.
- Семантика `PUT` (OBS-06), статус продавца (A2), жизненный цикл магазина (A1).

## Capabilities

### New Capabilities

_Нет._

### Modified Capabilities

- `seller-stores`: изменяются требования `Store creation`,
  `Store name uniqueness per seller` и `Store update`.

## Impact

- **seller-service:** `StoreServiceImpl` (`trim`, проверка с исключением
  магазина, `saveAndFlush` и перевод нарушения индекса в 409), `StoreRepository`
  (JPQL-запрос проверки), новый `src/main/resources/schema.sql`,
  `application.yaml` (два свойства SQL-инициализации).
- **БД `seller_service`:** новый уникальный индекс на `stores`. Его создает сам
  сервис при старте. Ручные проверки до и после запуска описаны в tasks, на
  production их нужно повторить.
- **Поведение при старте:** если в `stores` есть дубли по
  `(seller_id, lower(btrim(store_name)))`, seller-service не стартует, и это
  сделано намеренно, в отличие от молчаливого пропуска в C3.
- **catalog-service, frontend, Kafka, Keycloak:** без изменений.
- **Тесты:** unit-тесты в seller-service. Для проверок на реальном PostgreSQL
  выполняются ручные шаги на локальной БД (см. design.md, D5).
