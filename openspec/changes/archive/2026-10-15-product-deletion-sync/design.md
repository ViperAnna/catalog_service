# Design

## Context

- catalog-service: MongoDB одиночным узлом (без replica set) — многодокументных
  транзакций нет. Kafka используется только как consumer
  (`store-events-topic`, `catalog-group`, `DefaultErrorHandler` с DLT).
- Физическое удаление товаров: `ProductServiceImpl.deleteProductById`
  (владелец) и `StoreProductsPurger` (`STORE_PURGED`, сначала изображения,
  затем `remove` всех документов магазина; повтор доводит до конца).
  `deleteProduct` в `createProduct` — откат несостоявшегося создания, товар
  никому не был виден; событие не нужно.
- Архивация (`StoreProductsArchiver`, устаревший `STORE_DELETED`) меняет статус,
  не удаляет. Id товаров — ObjectId, повторно не используются.
- user-service: Kafka только producer (`user-created-events-topic` через
  outbox). Вишлист хранит id товаров в `wishlist_products`.

## Goals / Non-Goals

**Goals:** клиент не видит физически удаленные товары в вишлисте; их id
удаляются из вишлистов по событию; отсутствие ложных удалений (архивные и
заблокированные товары остаются); at-least-once.

**Non-Goals:** гарантия отсутствия id удаленных товаров в БД при любых гонках
(решение пользователя 2026-10-15: таблица удаленных товаров не вводится),
очистка при чтении, другие потребители события, автоматическая очистка
исторических id.

## Decisions

- **D1. Событие на каждый товар.** `PRODUCT_DELETED {eventId, occurredAt,
  productId, storeId}`, ключ productId, `product-events-topic` (3 партиции,
  `NewTopic` в catalog-service), конверт как в `seller-events-topic`.
  *Альтернатива:* одно событие на магазин со списком id — неограниченный
  размер сообщения; отклонено.
- **D2. Outbox в MongoDB до удаления, атомарный upsert.** Коллекция
  `outbox_events`, документ с `_id = "PRODUCT_DELETED:" + productId`,
  `productId`, `storeId`, `createdAt`, `status`. Запись — одна атомарная
  операция над одним документом (`findAndModify` с upsert):
  нет документа → создать PENDING; DISCARDED → снова PENDING с новым
  `createdAt` (повторная попытка удаления после неудачной); PENDING или SENT →
  не менять. Записывается до удаления документа товара. Для `STORE_PURGED` —
  после удаления изображений и непосредственно перед `remove` документов, чтобы
  долгое удаление изображений не расходовало окно D3.
- **D3. Публикатор с проверкой факта удаления.** `@Scheduled` раз в 3 с, по
  PENDING-записям в порядке `createdAt`:
  товара с productId нет → отправка в Kafka с ожиданием подтверждения 10 с,
  затем `status = SENT`;
  товар есть и записи меньше 1 часа → пропуск до следующего цикла;
  товар есть и записи 1 час и больше → `status = DISCARDED` и ERROR в логе.
  Ошибка отправки прекращает цикл. Событие публикуется тогда и только тогда,
  когда документа товара нет: товар не может появиться снова (ObjectId не
  переиспользуется, восстановления нет), поэтому проверка «отсутствует» не
  устаревает. *Альтернатива:* публикация сразу после удаления без outbox —
  теряется при сбое Kafka или процесса; отклонено.
- **D3a. Матрица сбоев.**
  | Сбой | Состояние | Итог |
  |---|---|---|
  | Запись outbox не прошла | товар не удален (удаление после записи) | ошибка запроса / повтор `STORE_PURGED`; события нет |
  | Запись прошла, удаление не прошло | товар есть, запись PENDING | событие не публикуется; через 1 час DISCARDED; повторное удаление вернет PENDING (D2) |
  | Удаление прошло, процесс упал до публикации | товара нет, запись PENDING | публикатор отправит после перезапуска |
  | Kafka недоступна | товара нет, запись PENDING | отправка при следующих циклах; DISCARDED невозможен, пока товара нет |
  | Отправка прошла, `SENT` не записан | товара нет, запись PENDING | повторная отправка, дубль; потребитель идемпотентен |
  | Потребитель user-service падает | сообщение в топике | 3 повтора, затем `product-events-topic.DLT`; разбор DLT вручную |
- **D4. Потребитель в user-service.** `@KafkaListener` на
  `product-events-topic`, `groupId = "user-service-group"`; PRODUCT_DELETED →
  `DELETE FROM wishlist_products WHERE product_id = :productId` (одна команда,
  идемпотентна). Неизвестный eventType — WARN и пропуск (как в
  catalog-service). `DefaultErrorHandler` (3 повтора по 1 с, затем
  `product-events-topic.DLT`). В `application.yml` — consumer-настройки со
  строковыми десериализаторами.
- **D5. Показ клиенту.** Клиент видит товары вишлиста только в
  `GET /wishlists/{id}` (а также в ответах добавления и удаления): products
  собираются через `POST /products/by-ids`, который физически удаленные товары
  не возвращает. Поэтому id удаленного товара, оставшийся после гонки (R1) или
  удаленный до этого change, клиенту не показывается — без изменения кода и
  API; requirement `Wishlist retrieval with products` закрепляет это явно.
  `productCount` в `GET /wishlists` остается числом сохраненных id (каталог
  при списке не вызывается): он может быть больше числа показанных товаров —
  так же, как для архивных и заблокированных товаров. frontend `productCount`
  не показывает. *Альтернатива:* считать в списке только товары, которые
  вернул каталог, — вызов каталога на список и потеря архивных и
  заблокированных в счетчике; отклонено.
- **D6. Очистка оставшихся id (ручная процедура, по запросу пользователя).**
  Отличить «удален» от «недоступен» может только MongoDB (by-ids скрывает
  оба), поэтому очистка — сверка напрямую:
  1. `SELECT DISTINCT product_id FROM wishlist_products` (БД `user_service`).
  2. В MongoDB `catalog_db.products` найти, какие из этих id есть
     (`find({_id: {$in: [...]}}, {_id: 1})`, ObjectId); отсутствующие —
     физически удаленные. Архивные и заблокированные товары в коллекции есть
     и в список на удаление не попадают.
  3. `DELETE FROM wishlist_products WHERE product_id IN (...)` для
     отсутствующих id; повторный запуск ничего не находит.
  Процедура покрывает и id, удаленные до этого change, и редкие остатки после
  гонки. *Альтернатива:* служебный эндпоинт каталога «какие id существуют» и
  периодическая задача в user-service — новый API и код ради редкого случая;
  отклонено ("не усложнять").
## Risks / Trade-offs

- [R1] Гонка добавления и удаления. Последовательность: user-service
  проверил товар (`GET /products/{id}` → 200) → каталог удалил товар →
  событие опубликовано и обработано (в вишлисте этого id еще нет) →
  транзакция добавления фиксируется → id остается в вишлисте навсегда.
  Окно — от проверки в каталоге до фиксации добавления (обычно миллисекунды,
  до 5 с при медленном каталоге), против задержки публикации (до 3 с цикла
  публикатора). Последствия: id остается в БД, `productCount` больше на 1;
  клиенту товар не показывается (D5). Риск принят решением пользователя;
  остатки удаляются процедурой D6.
- [R2] Удаление документа прошло частично (часть товаров магазина) → события
  уйдут только для удаленных; повтор `STORE_PURGED` удалит остальные, их
  записи уже есть (D2).
- [R3] Конфликт архивации с `add-order-service`: оба change меняют
  `integration-events` `Topic declarations`, `Event consumers`,
  `Services without event processing`. Второй архивируемый change объединяет
  свои изменения с уже синхронизированным текстом вручную до синхронизации.
- [R4] Публикатор в нескольких экземплярах catalog-service дублирует события —
  потребитель идемпотентен; catalog-service работает в одном экземпляре.
- [R5] user-service впервые становится consumer: при старте без Kafka
  поведение как у других consumer'ов (`integration-events` OBS-12).

## Migration Plan

1. Развернуть user-service (consumer) до catalog-service: при
   `auto-offset-reset` по умолчанию (`latest`) новая группа не получит события,
   опубликованные до ее подписки.
2. Развернуть catalog-service (outbox, публикатор, топик).
3. По запросу пользователя — процедура D6 (очистка id, удаленных до change).
4. Откат: вернуть прежние образы; outbox-коллекция и топик остаются.
