# Proposal

## Why

Владелец меняет данные магазина (`storeName`, `description`, `email`,
`phoneNumber`) через `PUT /stores/{id}` сразу, без проверки модератором.
Ранее принято архитектурное решение, что данные магазина меняются только через
модератора; заявок на изменение магазина в системе нет (`SellerApplication`
описывает только продавца).

Решения пользователя:
- отдельная заявка на изменение магазина, не связанная с заявками продавца;
- через модерацию проходят все поля магазина, включая описание;
- продавец отправляет изменение тем же `PUT /stores/{id}`;
- писем о заявках на изменение магазина в первой версии нет.

## What Changes

- **`PUT /stores/{id}` создает заявку** на изменение магазина вместо
  немедленного изменения: ответ 202 с заявкой, магазин до одобрения не
  меняется. Правила формата, нормализация телефона, `trim` имени и
  уникальность имени проверяются при подаче. У магазина может быть только одна
  заявка в статусе PENDING; при одновременной подаче это гарантирует частичный
  уникальный индекс БД.
- **Заявка на изменение магазина** (`store_change_requests`): магазин,
  предлагаемые значения полей, статус `PENDING` / `APPROVED` / `REJECTED`,
  комментарий модератора, даты. Поле со значением null в заявке не меняет
  текущее значение (как сейчас у `PUT`).
- **Очередь модератора:** `GET /moderator/store-change-requests/pending`,
  `GET /moderator/store-change-requests/{id}`, `POST .../{id}/approve`,
  `POST .../{id}/reject` с обязательной причиной. Правила как у заявок
  продавца: рассматривается только PENDING (иначе 409), свою заявку модератор
  не рассматривает (403). Одобрение применяет поля к магазину; при занятом
  имени или заблокированном магазине или продавце — 409, заявка остается
  PENDING. Последняя защита от дубликата имени — индекс
  `uq_stores_seller_store_name`; магазин при одобрении блокируется на запись,
  чтобы одновременное удаление не привело к ошибке.
- **Просмотр владельцем:** `GET /stores/{id}/change-requests` — заявки своего
  магазина по убыванию даты.
- **Удаление:** заявки удаляются вместе с магазином (удаление владельцем и
  окончательное удаление продавца).
- **api-gateway:** маршрут `/moderator/store-change-requests/**` на
  seller-service.
- **BREAKING (контракт `PUT /stores/{id}`):** ответ 202 с заявкой вместо 200 с
  измененным магазином. Известных клиентов нет: frontend `/stores` не
  вызывает, catalog-service использует только `GET /stores/{id}`, файлы
  `*.http` его не содержат. Описание OpenAPI строится springdoc по аннотациям
  и обновится само.

### Out of scope

- Письма модератору и продавцу о заявках на изменение магазина.
- Отмена заявки владельцем, редактирование PENDING-заявки.
- Очистка поля значением null (`seller-stores` OBS-06 не меняется).
- Модерация создания магазина (магазин по-прежнему создается сразу).
- События Kafka: catalog-service данные магазина не хранит.

## Capabilities

### New Capabilities

_Нет._

### Modified Capabilities

- `seller-stores`: заявка на изменение магазина и ее модерация; изменяются
  `Store update`, `Store name uniqueness per seller`,
  `Store phone normalization`, `Store response format`.
- `api-routing`: маршрут очереди модератора магазинов.

## Impact

- **seller-service:** новая сущность `StoreChangeRequest` и статус,
  репозиторий, `StoreServiceImpl.updateStore` (создание заявки),
  `StoreController` (202, список заявок), новый контроллер и сервис
  модератора, DTO запроса и ответа, `MessageKeys`, тесты (5 существующих тестов
  `updateStore_*` переписываются). Таблица создается `ddl-auto`, частичный
  индекс одной PENDING-заявки — `schema.sql`.
- **api-gateway:** путь в предикате маршрута seller-service.
- **catalog-service, notification-service, user-service, frontend, Kafka:** без
  изменений.
