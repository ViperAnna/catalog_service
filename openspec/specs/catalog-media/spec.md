# catalog-media Specification

## Purpose
Baseline (as-is) поведения catalog-service по хранению изображений категорий и
товаров в объектном хранилище MinIO: проверка загружаемых файлов, расчет хеша,
формирование ключа объекта и публичного URL, дедупликация загрузок, метаданные
изображения и публичный доступ к бакетам. Спецификация описывает фактическое
текущее поведение кода и конфигурации, а не целевое.

## Baseline Context
- Источник: ветка `feature/SAM1-14`, коммит `78cec79`. Для dev-окружения
  учитывается рабочая копия `docker-compose.yml` (незакоммиченная): образ
  `bitnamilegacy/minio` с `MINIO_DEFAULT_BUCKETS=categories:download,products:download`.
  В `docker-compose.prod.yml` бакеты создает контейнер `createbuckets`
  (`mc mb`, `mc anonymous set download`).
- Метод: статический анализ `FileStorageServiceImpl`, валидаторов изображений,
  `MinioConfig`, конфигурации compose и nginx. На dev-стенде анонимными
  запросами проверены чтение объекта, листинг бакета, запрет записи и
  проксирование через nginx `/minio/`. Тестов нет.
- Использование: `catalog-categories` (изображение категории) и
  `catalog-products` (изображения товара). Там описано, когда изображение
  загружается или заменяется.
- Секция Requirements нормативна. Секции Observations, Assumptions и
  Open Questions нормативными не являются. Поведение, помеченное как
  observation, зафиксировано потому, что так работает код сейчас. Изменять его
  нужно отдельным change.
- Профиль `generate-data` (`CategoryInitializer`, `ImageUploadService`) массово
  удаляет и загружает изображения. Это инструмент наполнения данными, он вне
  scope требований, его особенности отмечены в Observations.

## Requirements

### Requirement: Image storage buckets
catalog-service SHALL хранить изображения категорий в бакете `categories`, а
изображения товаров — в бакете `products` MinIO по адресу `minio.endpoint`. Если
бакета нет в момент загрузки, catalog-service SHALL создать его без настройки
политики доступа.

#### Scenario: Изображение категории
- **WHEN** загружается изображение категории
- **THEN** объект сохраняется в бакете `categories`

#### Scenario: Бакет отсутствует
- **WHEN** бакета `products` нет при загрузке изображения товара
- **THEN** catalog-service создает бакет `products` и загружает объект

**Observation**: OBS-07

### Requirement: Image content hash
catalog-service SHALL вычислять для каждого загружаемого файла хеш SHA-256 по
всему содержимому в виде строки из 64 шестнадцатеричных символов в нижнем
регистре. Этот хеш SHALL использоваться в ключе объекта и SHALL сравниваться с
сохраненным хешем, чтобы определить, изменилось ли изображение.

#### Scenario: Одинаковое содержимое
- **WHEN** два файла с разными именами имеют одинаковое содержимое
- **THEN** их хеши совпадают

### Requirement: Object key and upload deduplication
Ключ объекта SHALL иметь вид `<sha256>_<имя файла>`, где имя файла — последний
сегмент исходного имени файла, а при его отсутствии — `unknown.jpg`. Если объект
с таким ключом уже есть в бакете, загрузка SHALL пропускаться. Любая ошибка
проверки существования SHALL считаться отсутствием объекта.

#### Scenario: Повторная загрузка того же файла
- **WHEN** загружается файл с тем же содержимым и именем, что и существующий объект
- **THEN** новый объект не создается, используется существующий ключ

#### Scenario: То же содержимое, другое имя
- **WHEN** загружается файл с тем же содержимым, но другим именем
- **THEN** создается отдельный объект с другим ключом

**Observation**: OBS-05, OBS-09

### Requirement: Stored image metadata
Для каждого загруженного (или найденного по ключу) изображения catalog-service
SHALL сохранять в документе категории или товара объект
`{hash, url, fileName, size}`, где fileName — исходное имя файла в том виде, в
котором его передал клиент, а size — размер файла в байтах. Content-Type объекта
SHALL совпадать с Content-Type, переданным клиентом.

#### Scenario: Метаданные
- **WHEN** загружается файл "photo.jpg" размером 1000 байт
- **THEN** сохраняется Image с hash, url, fileName = "photo.jpg" и size = 1000

**Observation**: OBS-10

### Requirement: Public image URL
URL изображения SHALL формироваться при загрузке как
`<minio.public-endpoint>/<bucket>/<ключ объекта>` простой конкатенацией без
URL-кодирования и SHALL сохраняться в документе. Ответы API SHALL отдавать
сохраненный URL без пересчета.

#### Scenario: Формирование URL
- **WHEN** `minio.public-endpoint` = `http://localhost:9000` и загружается изображение товара "a.jpg"
- **THEN** url = `http://localhost:9000/products/<sha256>_a.jpg`

#### Scenario: Смена публичного адреса
- **WHEN** после загрузки меняется `MINIO_PUBLIC_ENDPOINT`
- **THEN** ранее сохраненные URL не меняются

**Observation**: OBS-03, OBS-04

### Requirement: Public read access to image buckets
Окружения развертывания SHALL настраивать бакеты `categories` и `products` с
анонимной политикой `download`: анонимное чтение объектов разрешено, анонимная
запись запрещена. В dev-окружении SHALL также разрешаться анонимный листинг
содержимого бакета. nginx фронтенда SHALL проксировать `/minio/` на MinIO.

#### Scenario: Анонимное чтение
- **WHEN** клиент без учетных данных запрашивает URL изображения
- **THEN** MinIO отдает файл с кодом 200

#### Scenario: Анонимная запись
- **WHEN** клиент без учетных данных выполняет PUT объекта в бакет `products`
- **THEN** MinIO отвечает 403

#### Scenario: Листинг бакета в dev
- **WHEN** клиент без учетных данных запрашивает `GET /products/` у MinIO
- **THEN** ответ 200 содержит список ключей объектов

**Observation**: OBS-08
**Assumption**: ASM-02

### Requirement: Image file validation
Изображение SHALL считаться допустимым, если файл не пуст и его Content-Type
входит в список допустимых или, если не входит, первые три байта равны
`FF D8 FF`. Для товаров список SHALL быть `image/jpeg`, `image/jpg`, для
категорий — `image/jpeg`, `image/jpg`, `image/pjpeg`, `application/octet-stream`.
Недопустимый файл SHALL давать 400.

#### Scenario: JPEG с неверным типом
- **WHEN** JPEG-файл передан с Content-Type `image/png`
- **THEN** файл принимается по сигнатуре

#### Scenario: PNG
- **WHEN** PNG-файл передан с Content-Type `image/png`
- **THEN** ответ 400

#### Scenario: Произвольный файл с типом image/jpeg
- **WHEN** текстовый файл передан с Content-Type `image/jpeg`
- **THEN** файл принимается

#### Scenario: Пустой файл
- **WHEN** передан файл нулевого размера
- **THEN** ответ 400

**Observation**: OBS-01, OBS-02

### Requirement: Upload size limits
catalog-service SHALL принимать multipart-запросы с файлом не больше 5MB и
общим размером запроса не больше 30MB (`spring.servlet.multipart`, переопределяется
`SPRING_SERVLET_MULTIPART_MAX_FILE_SIZE` и `SPRING_SERVLET_MULTIPART_MAX_REQUEST_SIZE`).

#### Scenario: Слишком большой файл
- **WHEN** одно изображение больше 5MB
- **THEN** запрос отклоняется до обработки контроллером

**Assumption**: ASM-03

### Requirement: No deletion of stored images by API operations
Операции API категорий и товаров (создание, изменение, удаление) SHALL NOT
удалять объекты из MinIO. Единственное исключение — окончательное удаление
магазина (STORE_PURGED): объект изображения товара удаляемого магазина SHALL
удаляться из бакета `products`, только если ни один товар другого магазина
не содержит изображения с тем же hash. Отсутствие объекта при удалении SHALL
NOT быть ошибкой. Бакет `categories` SHALL NOT затрагиваться.

#### Scenario: Удаление товара
- **WHEN** удаляется товар с изображениями через `DELETE /products/{id}`
- **THEN** объекты изображений остаются в бакете `products`

#### Scenario: Изображение только удаляемого магазина
- **WHEN** обрабатывается STORE_PURGED, и изображение используют только товары этого магазина
- **THEN** объект удаляется из бакета `products`

#### Scenario: Общее изображение
- **WHEN** обрабатывается STORE_PURGED, и изображение с тем же hash есть у товара другого магазина
- **THEN** объект остается в бакете

**Observation**: OBS-05, OBS-06

### Requirement: Storage error handling
Ошибка MinIO типа `MinioException` при загрузке SHALL давать ответ 503 с телом
`{message, time}`.

#### Scenario: Ошибка MinIO
- **WHEN** MinIO возвращает ошибку S3 при загрузке объекта
- **THEN** catalog-service отвечает 503

**Assumption**: ASM-01

## Observations (non-normative)
Поведение подтверждено кодом и может быть дефектом. В Requirements оно
зафиксировано как есть. Исправлять его нужно отдельным change после решения.

- **OBS-01. application/octet-stream проходит для категорий.** Для изображений
  категорий допустим `application/octet-stream`, а при допустимом типе
  сигнатура не проверяется, поэтому принимается любой файл с этим типом.
- **OBS-02. Content-Type клиента не проверяется по содержимому.** Файл с
  допустимым типом (например, `image/jpeg`) принимается без проверки сигнатуры,
  поэтому под видом изображения можно загрузить произвольный файл.
- **OBS-03. URL без кодирования.** Имя файла попадает в ключ и URL без
  кодирования. Пробелы, кириллица, `#`, `?` дают некорректные или битые URL.
- **OBS-04. URL фиксируется при загрузке.** Смена публичного адреса MinIO
  требует миграции данных. В dev-данных сохранен адрес `http://localhost:9000`.
- **OBS-05. Общие объекты.** Объект с одним ключом может использоваться
  несколькими категориями и товарами одновременно, поэтому удалить объект
  по ссылке из одного документа небезопасно.
- **OBS-06. Мусор не собирается.** Неиспользуемые объекты не удаляются и
  накапливаются.
- **OBS-07. Бакет без политики.** Бакет, созданный самим catalog-service
  (`ensureBucketExists`), не получает анонимной политики. Если бакет не создан
  заранее средствами окружения, публичные URL будут недоступны.
- **OBS-08. Анонимный листинг.** Анонимный листинг бакетов позволяет
  перечислить все загруженные изображения (проверено на dev-стенде).
- **OBS-09. Ошибки проверки существования скрываются.** Любые ошибки
  проверки существования (сеть, авторизация) считаются отсутствием объекта и
  ведут к повторной загрузке.
- **OBS-10. Разные имена в ключе и метаданных.** fileName в метаданных — сырое
  исходное имя, а в ключе используется только последний сегмент пути.
- **OBS-11. URL в generate-data.** В профиле `generate-data` `ImageUploadService`
  формирует URL существующих объектов через внутренний `minio.endpoint`
  (`http://minio:9000`) и без hash. Такие URL недоступны из браузера. Это
  инструмент, вне scope требований.

## Assumptions (unverified)
- **ASM-01. Недоступность MinIO.** Сетевые ошибки (MinIO недоступен), вероятно,
  не являются `MinioException` и дают 500 вместо 503.
- **ASM-02. Политика в prod.** В prod политика `mc anonymous set download`
  дает те же права, что и в dev, включая анонимный листинг. На prod не
  проверялось.
- **ASM-03. Превышение лимитов.** Оно, вероятно, дает ответ 413 стандартной
  обработкой Spring без тела `{message, time}`.
- **ASM-04. Публичный адрес в prod.** Значение `MINIO_PUBLIC_ENDPOINT` в prod
  неизвестно. Наличие nginx `/minio/` позволяет предположить адрес вида
  `https://<домен>/minio`.
- **ASM-05. Параллельная загрузка.** Параллельная загрузка одного и того же
  файла приводит к перезаписи объекта тем же содержимым.

## Open Questions
- **OQ-01. OBS-01–OBS-11.** Какие из них дефекты?
- **OQ-02. Форматы.** Нужно ли поддерживать форматы помимо JPEG (PNG, WebP)?
- **OQ-03. Неиспользуемые объекты.** Нужна ли политика удаления неиспользуемых
  объектов и как учитывать общие объекты?
- **OQ-04. Анонимный листинг.** Допустим ли анонимный листинг бакетов?
- **OQ-05. Хранение URL.** Хранить URL в документе или вычислять из ключа при
  выдаче?
